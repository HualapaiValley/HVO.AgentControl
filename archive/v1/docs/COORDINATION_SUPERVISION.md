# Coordination supervision

The C# `CoordinatorService` owns continuity and dispatch. OpenCode is a decision helper: the service supplies current evidence and asks it what work should happen next. The hosted two-second timer runs supervision and decision scheduling independently of native model execution, catches exceptions, and retries failed recovery persistence on subsequent ticks. A persisted service heartbeat refreshes every 30 seconds, including an intentional owner pause.

New coordinations in the UI default to **Keep supervising until I pause or stop**. API callers select `continuousSupervision: true`. Continuous mode has no fixed model-turn cutoff or artificial allowance window: `Round` counts lifetime decisions and `MaxRounds` applies only to bounded tasks. The model's `complete` result ends a planning pass, not supervision. A newly viable worker slot triggers immediate reassessment; results and questions also wake planning. When the available set and evidence remain unchanged, a persisted quiet-capacity deadline prompts a fresh assessment rather than a tight model loop.

The LLM selects tasks from supplied evidence and can request a worker to discover current repository documents, GitHub issues, PR heads, CI and dependencies. Task ordering must not become a hard-coded C# list. Normal waiting means there is no viable slot, planning/discovery is in progress, or an explicit service/owner constraint prevents dispatch. Worker uncertainty makes that worker unavailable without stopping unrelated viable workers. Missing participants and unavailable coordinator sessions remain observable service conditions that can be rechecked. An owner's pause or stop always wins; uncertain delivery is never replayed to appear busy. Provider dispatch/cooldown gates and bounded failure backoff remain authoritative (#82 tracks quota ingestion and model fallback).

Model fallback may itself use an advisory session (#82): C# detects a normalized provider failure, excludes the unavailable credential pool, and supplies an eligible candidate list plus task requirements, observed limits, cost and continuation evidence to another available model. Its structured recommendation must pass capability, owner-policy, readiness and spend validation. A bounded deterministic route is required if that adviser fails; exclude attempted routes to prevent recursive fallback loops. Native `session.status` retry/quota events must be consumed as well as terminal errors. Confirm that the old turn stopped and reconcile tool effects before creating a linked continuation attempt. This advisory fallback is planned, not implemented by this supervision change.

The coordination page shows the heartbeat, service state and scheduler reason separately from the native model's activity. Owner-assigned prompts created on participating workers during a run are included as bounded evidence with unchanged provenance. Earlier tasks and other workers are excluded from the result set; outstanding commands still occupy their worker's capacity.

When a continuous planning pass assigns no work despite viable capacity, C# requests one immediate scheduling review across the full owner-authorized scope. A blocked milestone/reviewer alone cannot establish that unrelated implementation, CI repair or approved PR finalization is unavailable. The adviser can request a broader bounded evidence audit, or report that the full authorized scope really has no eligible work. This does not force invented tasks or bypass permissions, review or CI gates.

The reviewed task/capacity/policy/CI-access fingerprint and trigger-command receipt persist in the coordination context. One unchanged state receives at most one extra review; progress tokens, refreshed permission timestamps, restart and ordinary quiet reassessment do not repeat that challenge. Real task, capacity or CI-access changes prompt fresh assessment. Explicit owner pause/stop, bounded-task mode, occupied or uncertain workers remain authoritative. This is a bounded planning challenge using the configured coordinator route, not automatic model escalation or proof that an LLM can never make a poor scheduling decision.

Planner context includes bounded CI-read permission observations per runtime, with source timestamps and explicit denied/unknown states. It never includes credentials. Missing GitHub access is not passing CI and does not block unrelated work. The service reacts to actual readiness changes rather than routine credential-observation timestamp refreshes.

`POST /api/v1/coordinations/{id}/renew` updates an existing paused checkpoint with idempotent `id`, `expectedRevision`, replacement `instruction`, `continuousSupervision`, and `additionalRounds` (zero for continuous mode). This enables supervision on an old exhausted run without replacing its identity, assignments, sessions, review receipts or update schedule. Previous policy is retained in an audit event. Unresolved coordinator delivery cannot be discarded through this endpoint. Bounded-task mode retains explicit turn grants and limits for callers that request them.

The eventual controller may run several advisory OpenCode sessions concurrently: work planning, worker/runtime maintenance, and operations/metrics analysis. Each receives dynamically built prompts from its relevant evidence. The C# service owns job queues, leases, dispatch validation and durable results so advisers cannot race to assign a worker or deploy incompatible changes. Deployment and recovery are themselves assignable work with verification and receipts; no special long-lived chat session or human babysitter should be required for normal operation. Multiple adviser queues and automatic deployment execution are follow-up scope; this change establishes the supervision boundary.

Planning should support a tool-driven question/answer loop. C# asks for a next task and suitable worker; the adviser can query built-in APIs or MCP for idle workers, capabilities, provider availability, repository documents and current GitHub issues/PRs. Tool responses carry observation times and revisions so the adviser can request missing evidence instead of receiving one ever-growing prompt. Its eventual proposal references task/repository, worker, model route and evidence. C# rechecks readiness and ownership and atomically claims/records dispatch; a stale proposal gets a conflict response and refreshed evidence, not duplicate work. Give each planning request a deadline and bounded tool budget, cancellation and an audit trail. Tool access is role-scoped: observation does not confer deployment or credential-management authority. The existing context/decision protocol is the first implementation; these query tools and concurrent advisory jobs are follow-up scope.

Regression evidence covers the real hosted timer continuing beyond an old turn cap after restart, no assignment replay, immediate capacity changes, model completion followed by a quiet reassessment, uncertainty isolated to one worker, explicit pause/stop, owner-assigned evidence, authenticated idempotent checkpoints, and published desktop/mobile controls.
