# Worker GitHub access

The `/github` owner page configures GitHub App access for an execution runtime. AgentControl stores the App private key encrypted and issues installation tokens restricted to the selected repositories, Contents/Issues/Pull requests write permissions, Checks/Commit statuses read permissions, and any compatible Actions read permission. It verifies the installation account, returned repository set, effective permission set and expiry before delivery. The private key never goes to a worker.

## Initial setup

1. Open [Register a GitHub App](https://github.com/settings/apps/new) while signed into the repository owner's account. Use a unique name such as `HVO-AgentControl-RoySalisbury` and the AgentControl repository URL as the homepage. No OAuth callback is needed for this installation-token integration. Disable the webhook; select installation only on your account.
2. Under repository permissions set **Contents**, **Issues** and **Pull requests** to **Read and write**. Set **Checks** and **Commit statuses** to **Read-only**. **Actions** read access is optional for exact-head CI conclusions; existing compatible Actions grants remain supported. Leave other permissions at their defaults. Metadata read access is implicit. This does not request checks/actions write, administration, organization management or workflow modification permissions. GitHub may require the installation owner to approve these expanded read permissions.
3. Create the App, note its numeric **App ID** from its settings page, and generate/download its PEM private key. The alphanumeric **Client ID** is not used by AgentControl.
4. In the App's settings sidebar choose **Install App**, then **Install** beside your account. Choose **Only select repositories**, initially only `RoySalisbury/HVO.AgentControl`, and install. Creating the App alone does not create an installation.
5. Open [Installed GitHub Apps](https://github.com/settings/installations) and choose **Configure** beside the App. The final number in the URL is the numeric **Installation ID**: for example, `https://github.com/settings/installations/12345678` means installation ID `12345678`. Organization installations use `https://github.com/organizations/ORG/settings/installations/12345678` instead.
6. In AgentControl's **GitHub** page select **Devcontainer .NET test**, enter the App ID, installation ID and `RoySalisbury/HVO.AgentControl`, and paste the PEM into the private-key field. Submit **Verify and configure access**. The field is cleared after submission. Never put the key in an agent prompt or chat.
7. Keep the runtime connected. The background service stores credentials in the managed GitHub CLI directory, then separately verifies that the exact owned server process uses that directory without a `GH_TOKEN` or `GITHUB_TOKEN` override. It shows **Ready**, **MigrationRequired**, or a visible **Blocked** reason. Existing personal GitHub configuration is not overwritten. All sessions using this runtime's OS account share the grant.

The owner must register/install the App in GitHub; possessing a repository deploy key or the host's existing `gh` login does not create an App installation automatically.

## Worker use and renewal

Credentials are written atomically to the runtime account's GitHub CLI `hosts.yml` with mode 600, in a protected canonical configuration directory. `gh` can then read issues, create PRs, publish reviews and comments within the selected repository permissions. No credential is passed in a shell command, prompt or command result. Native actions still need to obey assignment/project policy: GitHub write permissions themselves do not prevent merging.

Durable merge authority uses typed task and outcome fields rather than instruction or evidence text. An author assignment may start before a pull request exists by retaining its repository and `Author` role with pull request `0` and an empty head. After the native result settles, the owner records the exact published pull request and head in a typed `PublishedExactHead` result. Contributor provenance then remains attached to that repository and pull request across later head changes. A reviewer assignment carries the exact repository, pull request and head from the start, and its settled native result requires a typed owner-verified `ApprovedExactHead` outcome. Coordinator `send_prompt` actions can retain the same optional task scope, but the coordinator cannot verify its own result; the owner outcome endpoint remains the verification boundary. Ordinary prompts and plain evidence remain supported but cannot create review or merge authority, and legacy text is never upgraded by parsing.

Existing SSH Git deploy keys remain separate. For a new checkout that should use App credentials for Git, have the worker run `gh auth setup-git` and use the repository's HTTPS remote after verifying its identity. The delivery service does not rewrite repository remotes or personal Git configuration.

While the runtime is connected and healthy, AgentControl checks renewal every 30 seconds and replaces tokens within ten minutes of expiry. It periodically revalidates effective access against a versioned environment policy, the live owned process identity, and the exact AgentControl-owned credential file delivered most recently. A changed managed file is preserved and access becomes **Blocked**; AgentControl does not overwrite contents it can no longer verify. A credential can also be stored while effective access remains **MigrationRequired**. AgentControl does not restart an incompatible process because that could interrupt native work. Drain its work, use the existing owner-controlled stop operation, and reconnect the runtime; the fresh launcher reads the managed environment and readiness is verified again. Platforms where the exact process environment cannot be read remain explicitly blocked rather than being reported ready.

Failed issuance or delivery is marked Blocked and retried after two minutes. Configuration and delivery serialize, and both credential delivery and process-readiness evidence persist across web restarts. Each successful issuance records Checks, Commit statuses and Actions read evidence; Checks and Commit statuses are required for exact-head CI conclusions, while Actions remains optional. Older records remain Unknown until reverified. A denied permission is not evidence that CI is absent, and permission readiness is not evidence that checks passed. A PR check query must still bind results to the expected head revision and treat missing, unknown or pending checks as blocking. A previously issued credential can remain valid until its expiry even if renewal fails or a grant changes; it is not immediately revoked by replacement.

**Disable renewal** prevents further issuance/delivery by this integration. It retains the current credential and its displayed expiry. For immediate revocation, suspend or uninstall the App in GitHub. Disconnecting a runtime also suspends renewal, but does not revoke an already issued token. Keep this distinction when retiring containers.

## Validation and remaining work

Automated tests exercise JWT signatures/clock bounds, explicit scope, account mismatch, excess/missing access, expiry, error redaction, encrypted storage, authenticated/CSRF-protected settings, revision conflicts, disablement, and SSH delivery/rotation without replacing a personal login. The disposable SSH fixture also verifies that reconnecting to an existing process cannot claim a newly written environment, that token environment overrides are reported without their values, and that an explicit owned stop followed by a fresh start produces process-bound readiness. These tests do not prove live GitHub permissions.

With `HVO_GITHUB_CLI_TESTS=1`, the installed `gh` must also read an isolated fake credential produced by the actual writer. This caught a migration failure when the initial file omitted the App bot identity: CLI migration attempted a user lookup that installation credentials cannot satisfy. The writer includes both current and legacy token locations and the bot identity. CI runs this check; GitHub CLI must be installed for it.

The App is installed and live issue/comment, PR review, authenticated Git push and worker-created PR47 have been verified; see [advanced verification](validation/advanced-coordination-2026-09-07.md). Root still supervised fixes and merges. Durable publication intents and reconciliation of uncertain writes remain work in #44/#8; simply delivering a token does not make arbitrary `gh` writes exactly-once. Credential scope is currently per runtime, not per task/session. Automatic Dev Container provisioning remains tracked separately in #43.

Migration integration: the GitHub permission target model must retain all entities from chronologically earlier operator-update and telemetry migrations. Generated historical models describe their migration's schema, not every future schema change. The additive-history regression compares ordered migration entity sets and the final snapshot; future deliberate table retirement must supply explicit replacement/retirement evidence instead of weakening this check silently.
