# Shared provider circuit breakers (#82, first slice)

Native assistant provider errors now produce durable sanitized failure receipts tied to the managed command and native assistant message. Explicit structured quota codes park the provider; authentication errors require recovery. Generic 429 means throttled, not proven exhausted credit. 5xx means unavailable. Native OpenCode transport/authentication errors and malformed model output are not treated as evidence of upstream subscription exhaustion.

Commands pin a non-secret safety-group ID at dispatch. This initial implementation conservatively groups all runtimes using the same provider (`provider:opencode-go`, `provider:openai`, etc.). These are safety groups, not verified credential identities. Separate accounts on the same provider can therefore be over-blocked; explicit account bindings are follow-up work. Model overrides use their actual provider group. Go and ChatGPT do not share a group.

A transactional dispatch gate applies to coordinator and worker prompts, with a second check after native preflight. Already admitted/in-flight work is not aborted. Abort and permission replies remain available. Native OpenCode internal retries and unmanaged prompts are outside this gate. Native provider errors become visible through session reconciliation, so this does not promise instant detection before the provider emits evidence.

## Coordinator planning and admission

Coordinator contexts include optional `providerEvidence`: relevant shared-pool states/revisions, cooldown and recovery ownership, the latest sanitized failure receipt with its source worker/command, per-runtime instance/Go readiness, and bounded observed worker model catalogs. Shared-pool failures can originate from another worker. Earlier failure omissions, omitted models/variants and truncated pool lists are explicit. Visible pools prioritize configured defaults. Catalog selection retains the configured default and provider diversity, prioritizing providers without recorded holds; a large held catalog must not hide every observed alternative. Catalog metadata does not establish owner approval, pricing or remaining allowance. A missing pool means no recorded circuit hold only when `poolsTruncated` is false; otherwise its state is unknown. Neither absence nor `Available` verifies a subscription balance. Legacy contexts without this field remain readable and still receive current admission checks.

Before accepting any coordinator `send_prompt` action, C# rechecks the effective provider's runtime and pool readiness inside the same transaction that validates the whole batch. Omitting an override selects the worker default; changing models inside a held provider does not bypass the hold. A rejected action prevents all commands in that batch from being recorded and places bounded field-level correction into fresh recovery context. No provider state or recovery lease is changed by validation. Direct owner queuing retains its existing behavior and the normal dispatch gates still apply afterward.

An elapsed transient cooldown with fewer than three failures and no live/unknown prior attempt or conflicting recovery ownership is reported as `RecoveryEligible`. Both coordinator admission and actual dispatch use the same eligibility predicate; only dispatch acquires the existing single recovery lease. `RecoveryRequired`, exhaustion, authentication holds and unknown ownership remain held. Provider-readiness changes, recovery ownership changes, cooldown eligibility and catalog changes enter the planning fingerprint and permit reassessment of an otherwise quiet run. A separate observation key covers every relevant pool and complete observed route/variant identifiers, including entries omitted from the prompt. Context compaction retains that key, so omitted entries neither hide changes nor cause a continuous reassessment loop.

The parser also recognizes a supported nested `error.type` such as `usage_limit_reached` when no structured code is supplied. Generic 429s, error prose, malformed bodies and unknown types remain throttling evidence rather than proof of exhaustion. Raw provider bodies and readiness diagnostic text are excluded from coordinator provider evidence.

This is new-instruction admission and planning evidence, not automated fallback completion. It does not move existing queued commands, clear circuits, infer a quota reset, change worker defaults, enable paid access, replay uncertain tool effects, or consume advisory fallback receipts to create linked continuations. Those operations and the complete owner-approved cost/capability routing policy remain #82 work.

OpenCode `session.status` retry evidence is also reconciled. Only the supported structured `action.reason=account_rate_limit` with an action provider blocks the command's pinned execution-provider pool; generic retry prose and a generic 429 are not proof of exhausted budget. The native retry `next` value is retained only as an opaque retry-scheduler observation, never presented as a subscription reset or used to reopen the pool. A retry attempt is deduplicated durably per command and native attempt across polling and host restart. Raw native retry messages, action links, response bodies, and private URLs are not retained.

Throttle/outage cooldowns honor parseable Retry-After seconds or HTTP dates and add 1–5 seconds of jitter. Missing timing uses a 60-second cooldown; this is a retry policy, not a quota-reset estimate. After cooldown, exactly one queued managed attempt is admitted to recover the pool. Other attempts wait for terminal evidence. Three observed failures require owner recovery. Auth/exhaustion always require owner verification. A recovery lease survives restart and unknown outcomes hold dispatch; no failed command is replayed. Preflight failures or uncertain submission during recovery require inspection instead of automatic retry.

Model access shows observed state, unknown remaining allowance, retry time and workers whose defaults use the provider. Per-task overrides can affect additional workers; their queued command details identify the actual blocked group. Owner resume requires a fresh pool revision and explicit verification of provider access/allowance. It authorizes queued dispatch without rerunning failed work or buying access. Resuming does not prove a recovered provider; a subsequent failure blocks it again.

This slice does not estimate remaining subscription allowance from API prices, switch models, enable paid overage, provide multi-account credential bindings, or reconcile tool effects for fallback continuation. These remain #82/#69 work. Failure receipts and events retain only category/status/time and identifiers, never raw error messages or response bodies. Existing native transcript retention is unchanged.

After an account-limit retry, the safe next step is to reconcile the latest turn and its tool receipts, inspect any uncertain side effects, and have an owner verify recovery before resuming an eligible queued route. Linked continuation/fallback creation is not implemented by this slice.

## Advisory fallback receipts

The authenticated fallback recommendation API records an advisory replacement route only. It requires the source prompt's own durable assignment outcome and a structured provider-failure receipt for that command and pool. A historical retry receipt and a still-held pool do not prove that a task ultimately failed; a native retry followed by a successful final response is not eligible.

- A completed native failure has `Delivery.Finished` and assignment outcome `Failed`. Retained legacy turns with that pair remain eligible after restart without changing their delivery state or replaying them.
- An interrupted prompt with `Delivery.Cancelled` and assignment outcome `Cancelled` is eligible only with its own `Exhausted` receipt. Cancellation without proven quota exhaustion, including merely transient failures, is not a fallback cause. An `Abort` control command completes as `Finished` and is never itself a fallback source.
- Successful, in-flight, unknown, missing-outcome, transport-failed, and owner-cancelled completed turns are rejected. Eligibility never reads the mutable worker-wide outcome, which can describe a later task.

Each new receipt records the source delivery state, `SourceTaskOutcome`, source failure receipt ID/category, and source/target pool IDs. The request ID is idempotent and only one recommendation may bind a source command. Old advisory receipts retain an empty task-outcome field as unknown; the migration does not infer failure retroactively. Recommendations are historical validation receipts, not continuing authorization for dispatch.

Current worker revision/idle state, no outstanding work, configured target model, a distinct pool, and target readiness remain required. No work is dispatched, aborted, replayed, or resumed by this API. Receipt-aware tool reconciliation, owner-approved routing/risk/spend limits and a linked continuation remain #82 follow-up work.
