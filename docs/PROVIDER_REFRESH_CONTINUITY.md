# Provider refresh completion and process continuity

Applying the saved OpenCode Go key records credential storage separately from native cache refresh and model readiness. A confirmed auth PUT remains `StoredOnRuntime` if later refresh fails. `RefreshCompleted` requires observed disposal completion; Go dispatch additionally requires an owner-recorded external canary for that exact saved and delivered key revision. Saving revision 2 cannot reuse revision 1's readiness.

Before key delivery, the database installs a runtime-wide dispatch hold. The hold covers every provider because disposal affects an OpenCode workspace instance, including sessions using other providers. Managed outstanding deliveries and fresh per-directory native activity prevent disposal. SSH refresh includes worker directories, allowed roots, and the bootstrap/default instance directory where the launcher starts OpenCode. Direct control services use their canonical control directory.

The pinned OpenCode 1.18.29 `/global/event` disposal event contains the directory in both its outer envelope and `payload.properties`. It has no operation ID, PID, or process incarnation. AgentControl subscribes before POSTing `/instance/dispose`, requires agreement of both directory fields, and waits within a bounded cancellation deadline. POST acknowledgement and provider catalogue responses are not disposal-completion evidence. A missed event, ended stream, mismatched scope, failed acknowledgement, or cancellation leaves the runtime held. Acquired SSE responses are disposed even when POST fails.

A fresh transport-specific identity probe brackets subscription, completion, and the subsequent catalogue read:

- Linux SSH verifies the protected owner file and tmux owner, reads the current live pane PID and Linux kernel boot/start identity, and rejects a dead/replaced pane. It does not reuse or re-stamp `native-process-current`, cached `NativeProcess`, SSH connection state, or health/version responses. Platforms without the supported kernel evidence remain unverified.
- Direct HTTP reads the bound sidecar's identity manifest again and compares instance/incarnation. It does not fabricate a PID. This requires the owned sidecar entrypoint lifecycle, which rotates incarnation whenever the OpenCode service process starts; a process replaced outside that lifecycle is outside the supported ownership contract.
- Other transports must implement a fresh owned identity probe. The default interface implementation is unsupported and cannot release the hold.

The managed refresh service serializes its operations. Before each disposal POST, the instance receipt durably records a fresh attempt UUID, directory, and observed process identity. Only a matching event plus unchanged fresh process observations clears this pending marker. Event pruning and host restart do not clear it. Another Apply, including a new key revision, cannot reuse a same-process unresolved attempt: its late directory-only event could otherwise be mistaken for the new request. An explicitly requested Apply can supersede a pending attempt only after observing a different owned process, retaining the prior attempt and replacement evidence in the journal and creating a new UUID. No automatic native prompt or disposal replay is added.

This attribution assumes AgentControl exclusively controls disposal for its registered native service during refresh. Owners must not concurrently invoke native disposal/global-refresh APIs outside that scope. OpenCode does not provide an operation-correlated completion token that could prove attribution under concurrent external disposals. The SSE subscription itself is not durable; lost events remain uncertain rather than being reconstructed from a catalogue.

The migration marks legacy instance receipts in `Unknown` or `Refreshing` as unattributed pending work. Their new field is not treated as an empty safe history. With no retained old process identity, automatic retry remains held pending separately reviewed legacy recovery disposition; this change does not introduce an API to erase that uncertainty. No production database or provider operation is required to validate this migration.

Regression coverage exercises the actual service, SQLite store, provider dispatch guard, delayed native-shaped streams, failure disposal, process changes before POST/after event/after catalogue, unsupported/stale/foreign evidence, event pruning/restart/key rotation, legacy migration, the generated live Linux probe, and actual direct-HTTP manifest reads. Model inference is not part of these fixtures.
